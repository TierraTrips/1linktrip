Eventpages · Product proposal · November 2026

Simple first, then let it grow

Eventpages can already do a lot: type-specific details, live weather, travel, stays, food, transit, a guest itinerary and a packing list. What it has too much of is everything shown at once. This proposal does two things. It ranks what to build next for organizers, and it reworks the experience so a page starts small and grows one step at a time, the way setting up a new phone does.

The 5 changes I'd make first
  1. Replace the long form with a 4-screen setup. The setup asks for event type, then name and date, then venue, and then the page is done. Theme, sections and travel tools fill in from the event type.
  2. Grow pages through an "Add to your page" gallery. Cards relevant to the event type come first (RSVP, Room block, Packet pickup…), and each one opens a small focused form. The gallery replaces the 14-row section list and the generic links editor.
  3. Give guests four tabs instead of one 14-section scroll. The tabs are Event · Travel · Nearby · My trip. The first screen answers what, when and where; everything else is one tap away.
  4. Merge the overlaps. One trip bar (from, dates, guests) feeds flights, cars and hotels, and there is one place for directions. A guest's own bookings show inside the schedule, and one notes list replaces both "Details" and the duplicate type fields.
  5. Add hosted short links and accounts, sign-up last. With a link like eventpages.app/maya-theo, organizers can keep editing after they share. Setup and editing work without an account; the sign-up prompt appears only at Share. This is the first small server piece and the base for a paid planner tier and an iPhone app.

Guest page: one long scroll

  • What a guest needs on the day (time, place, directions, next item) sits on the same scroll as things needed weeks earlier (flights, hotels, packing).
  • The top navigation is 14 pills in a sideways-scrolling row. On example pages the "Example page" bar overlaps it (visible in the screenshots below).
  • The "Where to stay" section lists 8 hotels with 2 to 3 buttons each before the guest reaches the food section. The wedding's room block, the hotel the couple actually wants guests in, lives in a different section.
  • Three sections cover getting there. "Getting there", "Getting around" and "Map" each describe how to reach the venue, in different ways.

Editor: everything at once

  • One long form with 9 groups (Basics, Wedding details, When, Where, Look, Sections, Schedule, Packing list, Details and links) and 87 controls before anything is filled in.
  • Event type is a dropdown inside Basics, but it decides which fields exist and what the page looks like. It should be the first decision, not one field among many.
  • The Sections list has 14 rows with checkboxes and up/down arrows. Turning on a section that has no content changes nothing on the page, which looks broken.
  • "Details and links" overlaps the type fields (RSVP, Registry, Dress code).
  • First run: "Create a page" opens the full form. Publishing needs a title, venue and start date, but nothing marks them as the essentials.

3 · Guided setup: four screens, then done

Like setting up a new phone: one question per screen, a progress bar, Back and Skip. It asks only what a page can't work without. Everything else gets a sensible default and can be added later from the gallery (section 4). A ticket preview on the phone, and a live page preview on desktop, fills in as the organizer answers.

  1. What are you planning? Six cards. This sets the type fields, theme, suggested cards and which guest tools are on.
  2. What's it called, and when? Name, date and start time; end time is optional.
  3. Where is it? Venue search. This alone turns on weather, travel, stays, nearby places and the map. Skip shows "Venue to be announced".
  4. Your page is ready. Share, QR code, and the three most useful next additions for this event type. Tapping Share is where the account prompt appears (section 9).

Moved out of setup and given defaults: cover photo and colors (a theme per type), RSVP and dress code (suggested first in the gallery), schedule, notes and section order (a fixed, sensible order per type).

4 · "Add to your page": grow the page one card at a time

After setup, organizers add things the same way they add widgets on a phone. A gallery of cards puts the ones for this event type first. Each card opens a short form of two to four fields in a bottom sheet (phone) or dialog (desktop), and the card shows a check once it's on the page. Automatic guest tools are simple on/off switches, with no ordering to manage.

This one pattern replaces three things in today's editor: the 14-row Sections list, the "Details and links" editor, and the always-visible type fields.

8 · The editor after setup

Returning organizers get a short checklist instead of the long form. Each group is collapsed and shows its status (done, partly done, empty) and a one-line summary, and only one group is open at a time. Guest tools appear as a single "Automatic" row. The live preview stays on the right on desktop; on phones it is one tap away.

9 · Accounts: build first, sign up later

No account is needed to try Eventpages. Setup, the gallery and the editor all work with the draft saved on the device, as they do today. The prompt appears only when it gives something back:

  • At Share or Publish: "Keep your page. Edit it from any device and keep the same link." The options are Apple, Google or email, plus "Not now, copy the link", which keeps today's link-only behavior.
  • In the editor: a quiet "Save to use on other devices" row.
  • On sign-in, the local draft moves into the account unchanged. Nothing is retyped and nothing is lost.

This needs the server from idea 1. The same server also enables editing from several devices, the organizer dashboard, the paid tier and the iPhone app.

10 · Path to an iPhone app

Two routes
RouteWhat it meansTrade-off
Wrap the web app (for example Capacitor)The existing HTML/JS runs inside a native iOS shell, and native plugins and native extensions are added around it.Most code is shared with the website, so the app ships much sooner. The risk is App Store rejection if the app feels like a website in a box (see below).
Native rewrite (SwiftUI)A separate iOS app that talks to the same server.Best feel and full platform access, but a second codebase to build and maintain. Worth it later, if the app becomes the main way guests use Eventpages.

Recommendation: wrap first, and add real native features from day one so the app clears review. Rewrite only if usage justifies it.

App Store risk: guideline 4.2, "Minimum Functionality"

Apple's review guidelines say an app should offer more than a repackaged website. A thin wrapper around Eventpages would be at risk. How strictly reviewers apply this varies and can't be known in advance uncertain. The usual way to clear it is native features a website can't offer. Ones that fit Eventpages:

Native featureFor whomNeeds
Push notifications for schedule changesGuests: "Ceremony moved to 5:00 PM"Server plus Apple push setup; pairs with idea 6
Offline itineraryGuests without signal at the venue or abroadLocal storage in the app; the web version already caches pages offline
Apple Wallet pass for the eventGuests: date, venue, and a reminder on the lock screenPasses must be signed with an Apple developer certificate, so on the server
Share-sheet import of confirmationsGuests: share a hotel or flight email from Mail straight into My tripA native share extension that feeds the existing parseReservation function
Home-screen widget and Live Activity on event dayGuests: countdown and "next up" on the home and lock screenNative Swift code (WidgetKit, ActivityKit). Live Activities have a time limit, about 8 hours verify against current Apple docs

What to build now so the port is cheap

  • Server and accounts (ideas 1 and 5, section 9). Push, Wallet passes, syncing and in-app sign-in all depend on them.
  • A clean, versioned event data model. Event config, guest bookings and packing state as documented JSON that the server, website and app all read the same way. The event already carries a version field (v: 1).
  • Keep parsing behind one function. parseReservation already is, so the share extension can reuse it or a server version of it.
  • A domain you control (e.g. eventpages.app). Universal links, which open event links directly in the app, need a verification file served from the domain. A custom domain makes that straightforward.
  • Separate business logic from page rendering, so a native screen can be swapped in later without rewriting the rules.

Other things to know: Apple's developer program has an annual fee ($99 per year for individuals and companies). If the app offers Google sign-in, Apple's rules require an equivalent privacy-focused option, which in practice means Sign in with Apple check the current wording of guideline 4.8.

Small fixes that need no redesign

  • The example-page bar overlaps the sticky section nav on phones.
  • Trip dates appear twice (Getting there and Where to stay).
  • Turning on a section with no content does nothing visible. Hide that toggle until the section has content, or show it as "add details".
  • The title and tagline placeholders always show the wedding example ("Maya & Theo") whatever the event type.

Suggested order

  1. Guided setup and the "Add to your page" gallery (no server).
  2. Guest tabs and the consolidations (no server).
  3. Affiliate IDs, QR card and .ics/CSV import (no server).
  4. Hosted short links with sign-up at Share, then RSVP, live updates and insights (small server), which together lead into the planner tier.
  5. iPhone app: wrap the web app, adding push for schedule changes, Wallet pass, share-sheet import and an event-day widget.
